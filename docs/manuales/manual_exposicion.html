Minuto 0 a 3. Problema y modelo

Qué decir

El concesionario tiene tres sedes: Bogotá, Medellín y Cali. Antes, el inventario y las ventas estaban en hojas de cálculo. Un carro se podía vender dos veces y el precio de lista se confundía con el precio del día de la venta.

Abre el diagrama. Señala, sin apurarte:

  • Una sede tiene varios vendedores y varios carros. Eso es 1:N.
  • Un carro lo puede suministrar un proveedor y un proveedor suministra varios carros. La tabla del medio, CARRO_PROVEEDOR, es la N:M y guarda el costo de esa compra.
  • Una venta pertenece a un cliente, a un vendedor y a un solo carro. El carro no se repite en ventas.
  • USUARIO y AUDITORIA no son del negocio: una sirve para entrar y la otra la llena el trigger.

Frase de 3FN, si preguntan

El teléfono de la sede no está copiado en el vendedor. El monto de la venta sí se guarda, porque es el precio de ese día. Si mañana cambia el precio del carro, la venta vieja no se mueve.

Minuto 7 a 11. Administración en MySQL

Deja el navegador a un lado. En la terminal, desde la carpeta del proyecto:

./database/demo_permisos.sh

Qué decir

Consulta intenta insertar un cliente y MySQL responde 1142, permiso denegado. Luego intenta registrar una venta y responde 1370, no puede ejecutar el procedimiento. La pantalla ya se lo impedía. El SGBD también se lo impide, porque la aplicación entra con consulta_concesionario, no con root.

Si preguntan por REVOKE: a vendedor se le concedió borrar ventas y anularlas, y enseguida se le quitó. Por eso sp_anular_venta le da 1370.

./database/demo_procedimiento.sh

Qué decir

El vendedor llama sp_registrar_venta. El procedimiento abre una transacción, inserta y confirma. El trigger marca el carro vendido y escribe una fila en AUDITORIA. Un segundo insert del mismo carro lo rechaza el trigger, aunque alguien se salte la pantalla. El mensaje empieza por «Trigger:».

Aclara las dos cuentas: vendedor entra al sitio. vendedor_concesionario entra a MySQL. No se mezclan.

Minuto 11 a 13. Backup

./database/demo_backup.sh --confirmar

Qué decir

El script muestra las ventas, las borra y el conteo queda en cero. Luego restaura concesionario_backup.sql y las ventas de prueba vuelven. El backup se hizo con mysqldump, incluye rutinas y triggers, y no incluye los usuarios de MySQL. Esos están en 06_usuarios.sql. En este mismo servidor no hace falta recrearlos.

Este paso borra las ventas de la demostración y deja otra vez las dos ventas de mayo. Si lo corres antes de mostrar la aplicación, el Onix vuelve a Disponible. Haz el backup al final de la demo de pantallas.

Minuto 13 a 15. EXPLAIN

./database/demo_explain.sh

Qué decir

En VENTA el plan ya usa idx_venta_fecha, tipo range, porque el reporte filtra por fecha. Para ver el antes y el después con claridad, el script crea una tabla de laboratorio de 5000 filas. Sin índice el plan es ALL, key NULL, 5000 filas. Con idx_demo_fecha pasa a ref y baja a unas 6 filas. Al terminar, el script borra esa tabla. No queda en la base del negocio.

Si preguntan por qué no hay índice en la cédula o en el chasis: ya son UNIQUE, e InnoDB indexa también las llaves foráneas. Otro índice igual solo haría más lentos los insert.

El índice de carros empieza por el estado porque la pantalla filtra por Disponible o Vendido sin obligar a elegir marca. El prefijo izquierdo tiene que ser esa columna.

Minuto 15 a 20. Preguntas que suelen hacer

PreguntaRespuesta corta
¿Qué diferencia hay entre vista, procedimiento y trigger?La vista solo lee y no guarda datos. El procedimiento hace el trabajo cuando lo llamamos: toma el precio e inserta la venta. El trigger corre solo en cada insert o delete de VENTA, aunque nadie llame al procedimiento.
¿Por qué el trigger sí puede cambiar el carro y el vendedor no?El procedimiento es INVOKER: usa los permisos de quien llama. El trigger lo creó root, así que puede hacer UPDATE en CARROS. El vendedor no tiene ese UPDATE, y no le hace falta.
¿Por qué BEGIN dentro del procedimiento no abre la transacción?Dentro de un procedimiento, BEGIN abre el bloque. La transacción se abre con START TRANSACTION. Fuera, en demo_transaccion.sql, BEGIN sí es la transacción.
¿Por qué las dos ventas iniciales no están en auditoría?El script de datos corre antes que el de triggers. El trigger solo ve lo que pasa después.
¿Dónde están las credenciales?No están escritas en app.py. La plantilla vacía es config.example.env. Para la demo, Compose las pasa por variables de entorno. La aplicación nunca entra como root.
¿Cómo evitas inyección SQL?Las consultas usan %s. PyMySQL envía el valor aparte del texto SQL.
¿Por qué Flask y no una API con React?El enunciado pide conexión directa al SGBD. El navegador no puede abrir MySQL. Flask renderiza el HTML en el servidor y él sí abre la conexión.
¿Qué es el chasis?Es el número único del carro. En la base la columna se llama VIN, que es el nombre técnico de ese número. En la pantalla se llama Chasis.
¿Qué pasa si consulta intenta insertar desde la consola?Error 1142. Lo muestra demo_permisos.sh.
¿El backup trae los usuarios?No. Trae tablas, datos, vistas, procedimientos y triggers. Los usuarios se crean con 06_usuarios.sql.

Si algo falla en vivo

  • La página no abre: confirma que Docker está encendido y que el comando fue docker compose up --build. La dirección es el puerto 8080, no el 5000.
  • El reporte sale vacío: revisa que el año sea 2026.
  • No puedes vender el Onix: ya se vendió en un ensayo. Elige otro carro Disponible, por ejemplo el Sandero o el Spark.
  • La terminal dice que el socket no conecta: usa -h 127.0.0.1 y el puerto 3307. Los scripts de demo ya lo hacen.
