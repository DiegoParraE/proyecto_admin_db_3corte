1. Problema

El concesionario opera tres sedes: Bogotá (Calle 100 # 15-30), Medellín (Carrera 43A # 1-50) y Cali (Avenida 6N # 25-40). Compra vehículos a proveedores, los ofrece en una sede, los vende un asesor y después puede hacerles mantenimiento. Ese flujo estaba repartido en hojas de cálculo. Ahí aparecen tres fallas concretas:

  • Un mismo número de chasis se puede anotar dos veces, o un carro ya vendido se ofrece de nuevo, porque nada impide el segundo registro.
  • El precio de lista y el precio de la venta viven en el mismo lugar. Si el lista cambia, se pierde lo que el cliente realmente pagó.
  • Cualquiera que abre el archivo puede borrar ventas, ver datos que no le corresponden o llevarse la única copia. No hay usuarios, ni respaldo, ni rastro de quién vendió.

La aplicación guarda ese flujo en MySQL y lo opera con tres roles. El inventario deja de editarse a mano: una venta, hecha por el procedimiento o por un INSERT directo, dispara un trigger que marca el vehículo como vendido y escribe una fila de auditoría.

2. Alcance

Entra en esta entrega:

  • Sedes, clientes, vendedores, proveedores, vehículos, compra al proveedor, ventas y mantenimientos.
  • Login de la aplicación con administrador, vendedor y consulta.
  • Cuentas de MySQL con privilegios distintos, para la demostración en el SGBD.
  • Una vista de detalle, una vista de inventario disponible, una vista de ventas por sede, dos procedimientos y tres triggers.
  • Respaldo lógico y comparación de planes con EXPLAIN.

Queda fuera: contabilidad, nómina, pasarela de pagos, aplicación móvil y cifrado de disco. El mantenimiento no cambia el estado del inventario: un carro vendido también entra a taller.

3. Justificación del SGBD

Se usa MySQL 8.4 con motor InnoDB. El modelo ya existía en MySQL 8/9 (el dump de origen es de MySQL 9.6) y el curso pide, en el mismo motor, usuarios, un procedimiento, un trigger, un respaldo y EXPLAIN. InnoDB cubre eso sin cambiar de producto:

  • Transacciones y llaves foráneas. Borrar una sede que todavía tiene vehículos falla, en vez de dejar vendedores huérfanos.
  • Procedimientos, triggers y vistas, que son parte de la sustentación.
  • Cuentas y GRANT por tabla y por rutina. El usuario de consulta puede leer y no puede insertar.
  • EXPLAIN muestra si un índice entra al plan.
  • Hay imagen oficial de Docker, así el docente levanta la base con un comando.

PostgreSQL también serviría (tiene lo mismo y un planificador más explícito). SQL Server también. No se migró porque el esquema, los datos y los nombres de restricción ya estaban probados en MySQL, y reescribirlos solo para cambiar de motor no aportaba al problema del concesionario.

4. Modelo entidad-relación

Figura 1. Entidades de negocio. En terracota, los hechos: la compra al proveedor y la venta. El mantenimiento también referencia cliente y vendedor, ambos opcionales.

Cardinalidades que el esquema obliga:

  • Una sede tiene muchos vendedores y muchos vehículos. Un vendedor pertenece a una sede.
  • Un proveedor puede haber vendido varios carros al concesionario. Un carro puede tener varias compras registradas; en los datos de prueba hay una por vehículo.
  • Un cliente puede tener varias ventas. Un vehículo tiene como máximo una venta (UNIQUE sobre VENTA.CarroID).
  • Un vehículo puede tener varios mantenimientos. Cliente y asesor del servicio pueden ir vacíos.

Además de las entidades de negocio están USUARIO (login de la aplicación, sin relación con VENDEDOR) y AUDITORIA (la llena el trigger, no el formulario).

6. Normalización

Todas las tablas están en primera forma normal: cada celda es un solo valor. El teléfono no es una lista. La descripción del servicio es un texto, no un grupo repetido de repuestos.

Están en segunda forma normal. Las llaves primarias son un solo atributo (subrogadas), así que no hay dependencia parcial de una parte de la clave. En CARRO_PROVEEDOR la fecha y el costo dependen de esa compra, no del proveedor solo ni del carro solo.

Están en tercera forma normal y en BCNF. Los determinantes son llaves candidatas:

  • CLIENTE: ClientID y DNI determinan nombre, apellido, dirección y teléfono. DNI es llave candidata (UNIQUE), así que no hay dependencia transitiva hacia un atributo que no sea clave.
  • CARROS: igual con CarroID y VIN.
  • VENTA: VentaID determina el resto. CarroID también, porque un carro se vende una sola vez: es otra llave candidata. El nombre del cliente no está copiado en la venta; si lo estuviera, ClientID → Nombre dentro de VENTA violaría 3FN.
  • VENDEDOR guarda SedeID, no el teléfono de la sede. El teléfono depende de la sede y vive en SEDE.

VENTA.Monto_Total no es un dato calculable que haya que borrar para “normalizar”. Es el precio acordado ese día. CARROS.Precio_Venta puede cambiar mañana y la venta ya hecha no debe moverse. Depende de la venta, no del vehículo. Por eso el procedimiento copia el precio de lista al insertar y, de ahí en adelante, son dos hechos distintos.

Estado_Inventario sí se puede derivar de “existe una fila en VENTA”. Se guarda igual porque el inventario se consulta todo el tiempo y el trigger lo mantiene alineado con esa fila. Es una redundancia controlada, no un descuido: si se borra la venta, trg_venta_after_delete devuelve el carro a Disponible.

8. Objetos de la base

Vistas

Las tres se crean con SQL SECURITY INVOKER. Quien consulta usa sus propios permisos: si no puede leer VENTA, la vista tampoco le responde. DEFINER habría ejecutado la vista como root y un usuario limitado vería filas que sus GRANT no permiten.

  • vw_detalle_ventas: venta con nombre de cliente, vendedor, vehículo, sede, monto y forma de pago. Es la lista de ventas de la aplicación.
  • vw_inventario_disponible: vehículos en estado Disponible, con su sede.
  • vw_ventas_por_sede: cantidad y suma de ventas por sede. El resumen del reporte usa esta vista. El total es histórico, no depende del filtro de fechas.

Procedimientos

sp_registrar_venta(cliente, vendedor, carro, forma_pago) rechaza una forma de pago desconocida, lee el precio y el estado del vehículo, y hace el INSERT. No pide el monto: lo copia de Precio_Venta. También es INVOKER, así que el vendedor necesita INSERT sobre VENTA y SELECT sobre CARROS. No se usó SELECT … FOR UPDATE: con INVOKER ese bloqueo exige privilegio UPDATE sobre CARROS, y el vendedor no lo tiene a propósito. La doble venta la cierran el UNIQUE de CarroID y el trigger BEFORE.

sp_reporte_ventas(desde, hasta) devuelve el detalle del periodo. La pantalla de reporte lo llama. El usuario de consulta tiene EXECUTE sobre este procedimiento y no sobre sp_registrar_venta.

sp_anular_venta(venta_id) es el tercer procedimiento. Abre una transacción con START TRANSACTION, borra la venta y hace COMMIT. Si la venta no existe, o el trigger falla, el manejador ejecuta ROLLBACK. Dentro de un procedimiento la palabra BEGIN abre el bloque de código, no la transacción; por eso la transacción se escribe START TRANSACTION. Fuera del procedimiento, en base_de_datos/demo_transaccion.sql, se usa BEGIN como alias y un ROLLBACK que deja la base igual. La pantalla de anular venta llama a este procedimiento, no a un DELETE suelto. Solo el administrador puede ejecutarlo: a vendedor_concesionario se le concedió y luego se le revocó con REVOKE.

Triggers

Protegen la tabla, no un botón. Un INSERT desde la consola pasa por el mismo camino que la aplicación.

  • trg_venta_before_insert: si el carro no existe o no está Disponible, hace SIGNAL y la fila no entra. También exige monto mayor que cero.
  • trg_venta_after_insert: pone el carro en Vendido e inserta en AUDITORIA con USER().
  • trg_venta_after_delete: devuelve el carro a Disponible y audita la anulación. No lee VENTA dentro del trigger: MySQL no deja consultar la misma tabla que disparó el evento. No hace falta, porque uk_venta_carro garantiza una sola venta por vehículo.

El trigger queda creado por root. Por eso puede hacer UPDATE de CARROS aunque la sesión sea la del vendedor. Las dos ventas del script de carga no aparecen en auditoría: 02_dml.sql corre antes de 05_triggers.sql.

9. Plan de seguridad

Hay dos puertas y no comparten clave.

La puerta web está en la tabla USUARIO. La clave se guarda como PBKDF2-SHA256 con 260000 iteraciones y sal. El formulario compara con hmac.compare_digest. Si el usuario no existe, igual se calcula un hash, para no responder más rápido en ese caso. La sesión va en una cookie firmada, HttpOnly y SameSite=Lax. Cada POST lleva un token CSRF. Las consultas usan parámetros %s; el texto del buscador no se concatena al SQL. Los comodines % y _ del usuario se escapan antes del LIKE.

Al entrar, Flask no sigue conectado como root. Según el rol abre una de estas cuentas, definidas en 06_usuarios.sql para el host % (conexión TCP):

Cuenta MySQLUsoPuedeNo puede
auth_concesionarioSolo el loginSELECT sobre USUARIOVer ventas, inventario o hashes de otras tablas
consulta_concesionarioRol ConsultaSELECT de negocio y EXECUTE de sp_reporte_ventasINSERT, UPDATE, DELETE, vender, leer USUARIO o AUDITORIA
vendedor_concesionarioRol VendedorLeer el negocio; insertar y actualizar clientes; insertar ventas y mantenimientos; ejecutar ambos procedimientosBorrar, cambiar una venta ya hecha, actualizar el precio del carro, leer auditoría
admin_concesionarioRol AdministradorALL dentro de concesionario_dbNo es superusuario del servidor: no administra otras bases ni crea cuentas globales
rootCarga inicial y backupEl servidorNo lo usa la aplicación

En la sustentación, consulta_concesionario ejecuta un INSERT y MySQL responde 1142. Ese es el control del SGBD. El formulario esconde el botón, y además la cuenta no tiene el privilegio: las dos capas tienen que fallar. Ningún GRANT lleva WITH GRANT OPTION.

Límite que hay que saber decir: el proceso de Flask conoce las cuatro claves, porque están en variables de entorno para poder abrir la conexión del rol. Si alguien toma el servidor de la aplicación, tiene esas claves. Lo que esta división sí impide es que un error del programa ejecute un DELETE con la sesión del vendedor: MySQL lo niega igual. En producción se quitan los usuarios de prueba de la pantalla de login, se rotan las claves y MySQL no se publica a internet; solo la red interna de Docker debería ver el puerto 3306.

10. Plan de respaldo

El respaldo de la entrega es lógico, con mysqldump --single-transaction --routines --triggers --events --set-gtid-purged=OFF --databases concesionario_db. --single-transaction saca una foto consistente de InnoDB sin bloquear las lecturas. El archivo queda en base_de_datos/concesionario_backup.sql y se regenera con ./base_de_datos/generar_backup.sh.

11. Análisis de índices

InnoDB ya indexa la llave primaria, cada UNIQUE y la columna de cada llave foránea. Crear otro índice igual no acelera la lectura y sí frena cada INSERT y cada UPDATE, porque hay que mantener dos estructuras. Por eso no existen idx_cliente_dni, idx_carro_vin ni un índice extra sobre VENTA.CarroID: ya son únicos. Tampoco se indexó AUDITORIA.Fecha_Hora. El autonumérico crece con el tiempo y “los últimos eventos” se resuelve con ORDER BY AuditoriaID DESC.

Los cuatro índices de 07_indices.sql responden a una consulta que de verdad se ejecuta:

ÍndiceColumnasConsulta que lo justifica
idx_venta_fechaVENTA(Fecha_Venta)sp_reporte_ventas, filtro BETWEEN de fechas
idx_carro_estado_marcaCARROS(Estado_Inventario, Marca)Pantalla de inventario. El estado va primero porque se filtra solo, sin marca. El prefijo izquierdo tiene que ser esa columna; al revés, WHERE Estado = 'Disponible' no usaría el índice
idx_cliente_apellidoCLIENTE(Apellido)Búsqueda por prefijo, Apellido LIKE 'Gom%'. Un LIKE '%omez' no lo usa, y el formulario no arma el patrón así
idx_manto_fechaMANTENIMIENTO(Fecha_Servicio)Historial de taller por fecha

Un índice no se “usa” por existir: el optimizador compara costos. Con pocas filas a veces le sale más barato leer la tabla entera. Por eso la sustentación no se queda en las dos ventas de mayo. demo_explain.sql hace las dos mediciones y borra la tabla de laboratorio al final. La consulta de laboratorio tiene la misma forma que un filtro del reporte: igualdad sobre la fecha.

Lectura del plan, que es lo que hay que señalar en pantalla:

  • Antes: type = ALL, key = NULL, rows cerca del total de la tabla. MySQL va a mirar todas las filas.
  • Después: type = ref, key = idx_demo_fecha, rows mucho menor. Entra por el índice y solo revisa las filas de esa fecha.

12. Arquitectura de la aplicación

Figura 2. Cada petición autenticada usa la cuenta MySQL del rol, no una cuenta única de la aplicación.

El código está en app/backend/app.py. Las pantallas están en app/frontend. No hay ORM: el SQL que se sustenta es el que está escrito en las rutas. Gunicorn levanta dos procesos. La sesión firma la cookie con SECRET_KEY; el rol no viaja en un campo que el navegador pueda editar sin invalidar la firma.

Matriz que aplica el programa, y que las cuentas de la sección 9 vuelven a exigir:

MóduloAdministradorVendedorConsulta
ClientesCRUDCrear y editarVer
Vehículos, sedes, vendedores, proveedoresCRUDVerVer
VentasCrear y anularCrearVer
MantenimientosCRUDCrearVer
ReporteVerVerVer
AuditoríaVerNoNo

Registrar una venta no hace INSERT desde Python. La ruta llama CALL sp_registrar_venta(...). El procedimiento escribe VENTA, el trigger BEFORE valida, el trigger AFTER cambia CARROS.Estado_Inventario y deja el rastro. Anular la venta, solo el administrador, dispara trg_venta_after_delete. El estado del vehículo no tiene campo en el formulario: si se pudiera digitar “Vendido”, el trigger y la pantalla se contradirían.

El archivo de ejemplo app/backend/config.example.env no trae claves. docker-compose.yml sí trae las de la práctica, porque el enunciado pide un comando único y los usuarios de prueba publicados en el README.

13. Manual de instalación

Con Docker, que es la vía de la entrega

  1. Instalar Docker Desktop y abrirlo.
  2. En la raíz del repositorio: docker compose up --build.
  3. Abrir http://localhost:8080. MySQL queda en 127.0.0.1:3307 (usuario root, clave root). Esos puertos evitan el MySQL que ya escucha en 3306 y AirPlay en el 5000.
  4. La primera vez se ejecutan, en orden, 01_ddl.sql … 07_indices.sql.
  5. Generar el backup de la sustentación: ./base_de_datos/generar_backup.sh.

Para volver a la carga inicial, incluyendo el borrado de ventas hechas en el ensayo: docker compose down -v y otra vez docker compose up --build. Sin -v el volumen sigue y los scripts no se repiten.

Sin Docker

Hace falta MySQL 8 o superior y Python 3.11+. Si el binlog está activo, el servidor debe tener log_bin_trust_function_creators = 1 antes de crear triggers, o hay que crearlos con una cuenta que tenga el privilegio. Luego:

mysql -h 127.0.0.1 -uroot -p < base_de_datos/01_ddl.sql
mysql -h 127.0.0.1 -uroot -p < base_de_datos/02_dml.sql
mysql -h 127.0.0.1 -uroot -p < base_de_datos/03_vistas.sql
mysql -h 127.0.0.1 -uroot -p < base_de_datos/04_procedimientos.sql
mysql -h 127.0.0.1 -uroot -p < base_de_datos/05_triggers.sql
mysql -h 127.0.0.1 -uroot -p < base_de_datos/06_usuarios.sql
mysql -h 127.0.0.1 -uroot -p < base_de_datos/07_indices.sql

En app/: crear un entorno, pip install -r requirements.txt, copiar config.example.env a .env, completar las claves y ejecutar flask --app app run --port 8080.

Comprobación rápida

  • Login admin / admin123, vendedor / vendedor123, consulta / consulta123.
  • El reporte, con fechas del 1 de enero al 31 de diciembre de 2026, muestra las ventas de mayo.
  • ./base_de_datos/demo_permisos.sh termina con el INSERT rechazado.
  • ./base_de_datos/demo_procedimiento.sh deja una fila en AUDITORIA y el segundo insert lo rechaza el trigger.
